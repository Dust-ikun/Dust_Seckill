# 秒杀链路文档（接手先读这一份）

> **这份文档解决什么问题**：本项目把「校验 + 扣库存」从数据库搬到了 Redis，又把「落库」从请求线程搬到了
> 后台投递器与消费线程。链路一旦拆开，最难的就不再是写代码，而是回答三个问题：
> **一次下单都经过哪些环节？每个环节失败会怎样？漏掉的东西谁负责发现？**
> 本文按这三问组织，读完应当能独立排查线上问题。
>
> **读法建议**：第 0、1 节通读；第 4、5 节的表格贴在工位上；真出问题时直接跳到第 7 节（运维手册）。
>
> **与代码不一致时以代码为准**。关键结论都标了 `文件:行`，且这些注释是随代码一起维护的。
> 本文基于 2026-10 的代码状态（对账口径含「已放弃 / 陈旧未了结」两类剔除、库存校准带值比对）。

## 0. 30 秒速览

### 0.1 一句话架构

| 层 | 做什么 | 不做什么 |
|---|---|---|
| Redis + Lua | **资格判定**：库存够不够、是不是同一人重复下单、原子扣减 | 不落任何业务数据 |
| MySQL `orders` | **订单状态机**：PENDING → CONFIRMED / CANCELLED | 不在请求线程里扣库存 |
| MySQL `seckill_outbox` | **待投递凭据**：这笔预扣一定要有人去投消息 | 不保证「只投一次」（靠消费端幂等） |
| RocketMQ | 把「确认订单 + 扣库存」搬到独立线程池 | 不保证不重复（至少一次语义） |
| MySQL `compensate_task` | **动作待办表**：没做完的归还动作，独立于任何线程存活 | 不是幂等表（幂等靠唯一索引 / Lua 去重键） |
| 对账（`StockReconcileService`） | 比对两侧真实状态，发现上面几条链路**照不到**的偏差 | 不抢正在跑的流量（有闸门、有值比对） |

### 0.2 三条硬规则（所有取舍都由它们裁决）

1. **宁可少卖，绝不超卖。** 两个方向的代价不对称：少卖可以被对账发现并补回，超卖无法修复（用户已经付钱/占位）。
   所有「顺序」类决策都据此裁定：**先让订单不成立，再归还库存**；**先落库状态，再执行动作**。
2. **状态只有一处真相，且必须先落库。** 任何「改完内存/Redis 再顺手做另一件事」的写法，都会在进程消失时留下无法追溯的中间态。
   因此：放弃投递 = 一个事务里写 `FAILED` + 写归还待办；归还动作由待办表驱动，而不是由调用栈驱动。
3. **对账的判据必须能证伪。** 不用「受理总数 − 确认数」这类推算做在途数，只用数据库事实：
   `可信在途 = PENDING 预订单 − 已放弃未了结 − 陈旧未了结`。

### 0.3 端口与入口

| 项 | 值 |
|---|---|
| 业务端口 | `8081`（`/seckill/**`、`/stock/{id}`） |
| 运维端口 | `9091`，只绑 `127.0.0.1`（`/actuator/health`、`/actuator/prometheus`） |
| 数据库 | MySQL `seckill`（`src/main/resources/db/schema.sql`） |
| Redis | `seckill:stock:{id}` / `seckill:bought:{id}` / `seckill:restored:{id}:{orderNo}` |
| MQ | RocketMQ `seckill-order-topic`（tag `create-order`），`seckill.mq.enabled=false` 时整条 MQ 链路退化为同步落库 |

## 1. 正常链路：一次成功下单的完整时序

```
客户端               请求线程                    MySQL                 Redis          后台投递器        消费线程
  │  POST /seckill      │                          │                    │                │                │
  ├────────────────────▶│                          │                    │                │                │
  │                     │ ① Lua 原子预扣 ──────────┼───────────────────▶│                │                │
  │                     │    SISMEMBER / DECRBY / SADD                  │                │                │
  │                     │ ② 一个本地事务 ──────────▶│                    │                │                │
  │                     │    INSERT orders(PENDING)│                    │                │                │
  │                     │    INSERT outbox(PENDING)│                    │                │                │
  │  202 QUEUED+orderNo │◀─────────────────────────┤                    │                │                │
  │◀────────────────────┤ ③ 立即返回（RT 里没有热点行写入）              │                │                │
  │                     │                          │                    │                │                │
  │                     │                          │  ④ 每 1s 扫 PENDING │                │                │
  │                     │                          │◀───────────────────┼────────────────┤                │
  │                     │                          │  markSent(SENT)    │  批量投 MQ ────▶│                │
  │                     │                          │                    │                │  ⑤ 消费 ──────▶│
  │                     │                          │  ⑥ 一个事务：UPDATE orders→CONFIRMED + UPDATE stock−1   │
  │                     │                          │◀───────────────────┼────────────────┼────────────────┤
  │  GET /order/status  │                          │                    │                │                │
  ├────────────────────▶│  读 orders.status ──────▶│  CONFIRMED → SUCCESS                │                │
```

逐步说明（**每一步的「为什么是这个顺序」都要记住，改顺序前先读第 4、5 节**）：

| 步 | 代码入口 | 写什么 | 关键点 |
|---|---|---|---|
| ① | `StockCacheService.tryDeduct` → `lua/seckill_deduct.lua` | Redis：`DECRBY stock`、`SADD bought` | 一次原子脚本内完成「查库存 → 判重复 → 扣减 → 打标记」；返回码 `-1/-2/-3/-4` 分别对应库存不足/重复/未预热/参数错 |
| ② | `SeckillPersistenceService.createPending` | MySQL：`orders(PENDING)` + `seckill_outbox(PENDING)` | **同一事务**。「订单已受理」与「消息一定会被投递」必须一起成立，这是本地消息表的语义落点 |
| ③ | `SeckillService.acceptWithOutbox` | — | 返回 `QUEUED + orderNo`。请求线程到此结束，后续不再依赖它存活 |
| ④ | `OutboxDispatchTask.dispatch` → `OutboxService.dispatchDue` | MySQL：`status='SENT'` | 先批量发、失败退回逐条；每条的失败处置（退避/放弃）是**按单条**语义 |
| ⑤ | `SeckillOrderConsumer.consumeOne` | — | MQ 至少一次，重复投递是常态不是异常 |
| ⑥ | `SeckillPersistenceService.confirm` | MySQL：`orders→CONFIRMED` + `stock−1` | **同一事务**；以「状态流转影响行数」为扣库存的许可证（1 行才有权扣一次） |

### 1.1 三条降级路径（不走 ①②③ 的正常形态）

| 触发条件 | 代码路径 | 形态 | 代价 |
|---|---|---|---|
| Redis 抛 `DataAccessException` | `SeckillService.persistSynchronously`（先 `probePreDeducted` 尽力探测是否已生效） | `persist()`：插入 `orders(CONFIRMED)` + `stock−1` 同一事务 | 无 Redis 前置过滤，全部压力打到数据库行锁；且 Redis 侧事后会与数据库**漂移**（靠对账 `REDIS_AHEAD` 发现） |
| MQ 未启用（容器里没有生产者） | 同上 | 同上 | 同上 |
| `seckill.outbox.enabled=false` | `SeckillService.acceptWithoutOutbox` | 建 PENDING 订单后**请求线程直投 MQ**；投递失败则取消订单 + 归还预扣 | 放弃「消息一定要投出去」的凭据。进程在「订单已建、消息未投」之间消失 → 订单永久 PENDING，**对账也报不出来**（没有 FAILED 凭据可依据），见第 10 节 |

## 2. 三张表 = 三个状态机

### 2.1 `orders`（订单）

```
                    ┌──────────────┐
   请求线程建单 ───▶ │   PENDING    │
                    └──┬────────┬──┘
       消费确认成功 ────┘        └──── 消费重试耗尽 / 对账修复
       （+扣 DB 库存）                 （+归还 Redis 预扣）
              ▼                              ▼
       ┌──────────────┐              ┌──────────────┐
       │  CONFIRMED   │              │  CANCELLED   │
       └──────────────┘              └──────────────┘
```

- `uk_order_no`：单号唯一（Snowflake），兼任消费幂等键。
- `uk_user_stock`：一人一单的数据库兜底（Redis SADD 是快路径，它是最后一道防线）。
- **状态即许可证**：`confirmOrder` 是 `UPDATE ... WHERE status='PENDING'`，影响 1 行才有权扣一次库存。
- `idx_orders_stock_status`：对账统计在途用它。

### 2.2 `seckill_outbox`（本地消息表）

```
   PENDING ──投出成功──▶ SENT ──(归档：超过保留期后删除)
      │
      └──重试耗尽──▶ FAILED（终态；与一条 CANCEL_ORDER 待办同事务落库）
```

- **所有 UPDATE 都带 `AND status='PENDING'` 守卫**（`OutboxMessageMapper`）：投递器不做抢占，同一行可能被多实例同时捞起。
  没有守卫时两个方向都会出事：把已投出的消息改回 `FAILED` → 对已投出的单回补（用户「抢到了」又被取消）；
  把已放弃的记录改回 `SENT` → 在库存已归还的前提下再消费一次。
- `markFailed` 的**影响行数**是「谁有资格登记归还待办」的闸门：并发下只有一个实例拿到 1 行。
- 归档只删 `SENT` 且超过 `retention-hours` 的记录；`PENDING` / `FAILED` 永不自动删除（它们是欠账凭据）。

### 2.3 `compensate_task`（动作待办表）

```
   PENDING ──执行成功 / 确认无需处理──▶ DONE
      │
      └──重试耗尽──▶ FAILED（等人工；**仍算「未了结的归还义务」**）
```

| type | 动作 | 用在什么场景 | 幂等靠什么 |
|---|---|---|---|
| `ROLLBACK_ALL` | 库存 +1 且**摘掉**已购标记 | 这次下单根本没在库里留下自己的订单行（写预订单失败、单号冲突、降级落库失败） | `SREM` 标记的返回值（摘到标记的那一次才有资格加库存） |
| `RESTORE_STOCK_ONLY` | 库存 +1，**保留**标记 | 用户其实已经买过；消费端取消订单后的归还 | `seckill:restored:{id}:{orderNo}` 的 `SET NX EX` |
| `CANCEL_ORDER` | **先**把订单 PENDING→CANCELLED，确认后**再**库存 +1、保留标记 | 消费端重试耗尽且取消失败；投递端重试耗尽（放弃投递）；对账为「已放弃 / 陈旧」补登记 | 同上（NX 键），且「订单不成立」本身也是前置条件 |

> `CANCEL_ORDER` 为什么必须「先取消」：订单若仍是 PENDING，MQ 重投随时可能拿到许可证并真实扣减库存，
> 那时库存已被归还 → 超卖。**顺序不可颠倒**，这条与消费端的处置顺序是同一条规则（`CompensateType` 注释）。

### 2.4 Redis 侧的东西

| key | 类型 | TTL | 谁写 | 说明 |
|---|---|---|---|---|
| `seckill:stock:{stockId}` | String | **无 TTL** | 预热 `SET`、扣减 `DECRBY`、归还 `INCRBY`、对账校准（带值比对） | 活动结束要显式 `DELETE /seckill/cache?stockId=`，否则会一直留着 |
| `seckill:bought:{stockId}` | Set | 24h，**只在键创建后的第一次写入时锚定，绝不刷新** | 扣减 `SADD`、仅回补 `SADD`、对账补标 | 一人一单的判据；到期时间固定 = 首次写入 + 24h |
| `seckill:restored:{stockId}:{orderNo}` | String | 24h | 仅回补脚本 `SET NX` | 「仅回补库存」的一次性去重键；TTL 必须长于「同一笔回补可能被重试的全部时间窗口」 |

三个 key 都用 `{stockId}` 作 hash tag（Lua 要求同 slot，为将来上集群留路）。

## 3. 不变量与判据（对账为什么这么判）

### 3.1 不变量

```
    Redis 库存 == 数据库库存 − 可信在途
    可信在途   = PENDING 预订单 − 已放弃未了结 − 陈旧未了结
```

### 3.2 为什么是「单向可证」

Redis 永远**先扣**、数据库**后扣**（消费确认才扣）。因此正常流程只能让 Redis 比数据库「扣得更多」（更小）：

| 观察 | 结论 | 可信度 |
|---|---|---|
| `Redis > 应有值` | 有扣减**绕过**了 Redis（降级写库） | **必然异常**（正常流程不可能产生） |
| `Redis < 应有值` | 预扣泄漏（少卖） | AUTO 模式下期望值已按全部可信在途放宽，仍对不上 → 泄漏 |
| `Redis == 应有值` 但标记数 < 订单数 | 有用户买到却没留下标记 | 会被 Redis 重新放行，DB 仍能兜住 |

### 3.3 「可信在途」为什么要减掉两类

「每一笔受理都会留下 PENDING 预订单，所以 Redis 与 DB 的差额 = PENDING 行数」——
这条推理有一个前提：**每条 PENDING 最终都会走向 CONFIRMED 或 CANCELLED**。两类单打破它：

- **已放弃未了结**：投递重试耗尽，消息永远不会再投出去，订单却停在 PENDING；
- **陈旧未了结**：消息投出去了但迟迟没人消费（消费者组挂掉、消息丢失），或根本没有凭据（outbox 关闭链路崩在中间）。

它们的危险不在于「少卖一件」，而在于**会把差值抵消掉**：把它们算作在途，等于给等式两边同时减一，
一笔真正丢失的预扣会被读成 `CONSISTENT` —— **看起来最健康的一种坏状态**。所以它们必须被单独数出来、单独报出来。

### 3.4 对账照不到的角落（诚实清单）

1. **「Redis 已扣、预订单事务未提交」之间的崩溃**：没有任何持久化记录，对账的输入（库存/订单/标记）在崩溃前后完全一致 → 报不出来。
   彻底消除需要让预扣本身可恢复（把扣减也落库，或依赖 Redis AOF + 幂等回放），那是另一层取舍。**当前只能靠人工/重新预热重置。**
2. **`outbox.enabled=false` 链路上「订单已建、消息未投」的崩溃**：同上，没有 FAILED 凭据可依据。
3. **读偏斜**：快照与 Redis 读数无法原子，若恰有一笔请求「已扣 Redis、还没插 PENDING」，本轮会把正常中间态读成 `REDIS_BEHIND(1)`。
   定时对账用排空门控规避；手动对账遇到差值极小的 `REDIS_BEHIND` 应先复核再动手。

## 4. 失败与补偿矩阵（最重要的一张表）

| # | 故障点 | 现象 | 谁负责处置 | 最坏结果 | 用户看到 | 怎么被发现 |
|---|---|---|---|---|---|---|
| 1 | Redis 预扣被业务拒绝（库存不足 / 重复下单） | 抛 `BizException` | 请求线程 | 无副作用 | 直接收到错误码 1000/1001 | 正常业务结果 |
| 2 | Redis 不可达 / 响应超时 | 命令可能已执行、可能没执行 | `probePreDeducted` 探测 → 降级同步落库 | 两侧漂移（Redis 比 DB 多） | 大多正常；漂移后「抢到了却下单失败」 | 对账 `REDIS_AHEAD` |
| 3 | 建单事务失败（写 orders/outbox 失败） | 抛异常 | 当场 `rollbackAll` 回补；失败则登记 `ROLLBACK_ALL` | 库存少卖 | 收到 5002 | 待补偿表 + 对账 `REDIS_BEHIND` |
| 4 | 崩溃在「预扣成功 ↔ 事务提交」之间 | 进程消失 | **无人负责** | 预扣永久丢失 | — | **不可发现**（第 3.4 节第 1 条） |
| 5 | Broker 抖动，投递失败 | 退避重试：延迟 2s 起指数翻倍（单次上限 5 分钟，`base=2` 时实际最大 128s），15 次重试 ≈ **19 分钟** | `OutboxDispatchTask` | 延迟，最终自愈 | 结果出来得晚 | `outboxPending` 短暂上升 |
| 6 | 投递重试耗尽 | `FAILED` + 归还待办同事务落库，随后立刻尝试归还 | `OutboxAbandonService` → 待补偿任务 | 归还失败时少卖 | 订单最终 CANCELLED | `outboxFailed` / 对账 `ABANDONED_PENDING` |
| 7 | 崩溃在「放弃」的两步之间 | 事务保证：要么还在 PENDING（下轮重试），要么两条都已落库 | 事务本身 | 无 | — | 由 #6 的机制覆盖 |
| 8 | 消息投出后 Broker 丢失 / 消费者组挂掉 | 订单长期 PENDING，Redis 预扣被占着 | 对账 | 少卖 + 用户订单被取消 | 长期 `QUEUED` | `STALE_PENDING`（默认只告警，`repair=true` 才补登记） |
| 9 | 消费确认失败（DB 抖动 / DB 库存不足） | MQ 重试（10s/30s/1min，最多 3 次） | `SeckillOrderConsumer` | 重试耗尽 → 取消订单 + 归还 | 最终 FAILED | `consumeFailed` / `consumeCancelled` |
| 10 | 取消订单这一步本身失败 | 不能归还库存（会超卖） | 登记 `CANCEL_ORDER` 待办 | 少卖 | 最终 FAILED | `compensatePending` |
| 11 | 重复投递（MQ 至少一次语义） | 订单已结案 | 消费端幂等命中，**不做任何动作** | 无 | 无感 | `consumedDuplicate` |
| 12 | 用户此前已购但 Redis 标记丢失 | 建单撞 `uk_user_stock` | 仅回补库存、**保留标记**，拒绝本次 | 无 | 收到 1001 | `restoreStockOnly` 计数 |
| 13 | 单号生成缺陷（撞库） | 建单撞 `uk_order_no` | 完整回滚 + 告警 | 无 | 收到 5000 | ERROR 日志 |
| 14 | 归还动作失败（Redis 又挂了） | 待补偿任务按退避重试（延迟 10s 起指数翻倍，10 次 ≈ **25 分钟**） | `MaintenanceTask` | 重试耗尽 → `FAILED` 等人工 | 无感 | `compensateAbandoned` |
| 15 | 对账发现的偏差（降级漂移 / 假阴性） | 两侧不一致 | 对账修复（有闸门，见第 6 节） | 不修则持续少卖/超卖错觉 | 可能「抢到了却下单失败」 | `REDIS_AHEAD` / `REDIS_BEHIND` |

## 5. 崩溃点清单：每个「两步之间」消失会怎样

排查线上问题时，「进程恰好在这里被杀」是最容易被忽略的一类。逐个对照：

| 两步之间 | 崩溃后的状态 | 会自愈吗 | 靠什么 |
|---|---|---|---|
| Redis 预扣 ↔ 建单事务提交 | Redis 少一件，库里什么都没有 | **不会** | 无（3.4 节第 1 条，已知取舍） |
| 建单事务提交（orders+outbox） | 两者都在（同事务） | — | 事务 |
| outbox 落库 ↔ 投递器扫描 | 记录停在 PENDING | 会 | 投递器每秒扫一次 |
| 消息投出 ↔ `markSent` | 记录仍是 PENDING，消息已在 Broker | 会 | 重投 + 消费端幂等（`uk_order_no` / 许可证） |
| `markFailed` ↔ 登记归还待办 | 不可能：**同一事务** | — | `OutboxAbandonService` |
| 登记待办 ↔ 立刻执行归还 | 任务停在 PENDING | 会 | `MaintenanceTask` 每 30s 扫到期任务 |
| `cancelOrder` 提交 ↔ `restoreStockOnly` | 订单已 CANCELLED，库存未归还 | 会 | 任务重试；归还靠 NX 去重键幂等 |
| `restoreStockOnly` 成功 ↔ `markDone` | 库存已归还，任务仍 PENDING | 会 | 重试 → 幂等命中（`-3`）→ 结案 |
| `confirmOrder` ↔ `UPDATE stock` | 不可能：同一事务 | — | `@Transactional` |
| 消费端 ACK ↔ 上述任一步 | 消息会被重投 | 会 | 至少一次 + 幂等 |
| 对账「读」 ↔ 对账「写」 | 库里没有被覆盖的痕迹 | 会 | 校准脚本的**值比对**（不通过就不写） |

## 6. 对账：口径、结论、动作

### 6.1 一次对账读什么

`OrderMapper.selectReconcileSnapshot` 用**一条 SQL** 取回五个数（必须同一时刻，分次查询会自己制造假不一致）：

| 数 | 含义 |
|---|---|
| `dbStock` | `stock.count` |
| `pendingOrders` | 该活动 PENDING 预订单数 |
| `abandonedPending` | 其中 outbox = `FAILED` 的（不会再有消息来确认） |
| `stalePending` | 其中 `create_time` 早于陈旧阈值的（**不含**上一类，两者互斥） |
| `dbOrderCount` | 该活动订单总数（含所有状态，用于标记缺失判定） |

Redis 侧再读两个数：剩余库存、已购集合规模；外加一个数据库数：未了结的归还义务条数。

### 6.2 六种结论与处置

| 结论 | 含义 | 默认动作（`auto-repair=false`） | `repair=true` 时 |
|---|---|---|---|
| `NOT_PREHEATED` | Redis 里没有库存 key | 报告「请先预热」 | 同左（**不**顺手预热：预热会清空已购集合，是有副作用的动作） |
| `CONSISTENT` | 两侧一致 | 什么都不做 | 同左 |
| `REDIS_AHEAD` | Redis 比应有值多 → 有扣减绕过了 Redis | ERROR 日志 + 指标 | 库存校准（带闸门与值比对） |
| `REDIS_BEHIND` | Redis 比应有值少 → 预扣泄漏（少卖） | ERROR 日志 + 指标 | 库存校准 |
| `MARK_MISSING` | 有订单却没标记，用户会被重复放行 | ERROR 日志 + 指标 | 补齐缺失标记（**只增不删**） |
| `ABANDONED_PENDING` | 有「已放弃、订单仍 PENDING」的单 | ERROR 日志 + 指标 | 补登记 `CANCEL_ORDER` 待办（**不动库存**） |
| `STALE_PENDING` | 有「陈旧未了结」的单 | ERROR 日志 + 指标 | 同上 |

> `ABANDONED_PENDING` / `STALE_PENDING` **优先于**库存差额判定：这两类单存在时，
> 「差额该由谁负责」这个问题本身没有答案（库存可能已经归还，也可能没有），所以先让它们有主。

### 6.3 三类修复动作，各自的闸门

| 动作 | 代码 | 闸门（不满足就不动手） |
|---|---|---|
| 库存校准 | `StockCacheService.syncStockIfUnchanged` → `lua/seckill_sync_stock.lua` | ① 无未了结归还义务（否则与待办重复 INCRBY = 库存虚增）；② **写入前的值比对**：读到的值与当前值不一致就放弃（否则会把读之后发生的那笔预扣覆盖掉） |
| 补登记归还待办 | `StockReconcileService.enqueueReleaseTasks` | 每个单号最多登记一条（`orderNosWithTask` 去重），登记失败下一轮再试 |
| 补齐已购标记 | `StockCacheService.addBoughtUsers` | 只增不删（漏标让用户多跑一次 DB，误删标记会让用户重抢） |

### 6.4 排空门控（以及它为什么必须封顶）

定时对账跑之前会问一次「链路排空了吗」（`MaintenanceTask.pipelineDrained`）：

1. **该活动还有 PENDING 的 outbox 记录吗？** 有 → 跳过本轮（这笔预扣确定还没落库）。
2. **已投出的消息都处理完了吗？** `mqSent - resolved > 0` → 跳过（仍在途，读数会抖）。
3. **但门控封顶**：若该活动最老的 PENDING 预订单已超过陈旧阈值（`pipelineStuck`），
   说明「没排空」不是忙、而是**卡住**了 —— 此时直接放行，让对账把 `STALE_PENDING` 说出来。

> 第 3 条是必需的：门控原本问的是「还在忙吗」，而消费者组挂掉时这个答案永远是「是」，
> 门控会一直关着 → 对账连报都不报 → 「消息没人消费」彻底静默。**门控不能挡住自己本该报出的问题。**

## 7. 运维手册

### 7.1 指标（Prometheus：`http://127.0.0.1:9091/actuator/prometheus`）

命名规则：Micrometer 的 `.` 在 Prometheus 出口变成 `_`，Counter 追加 `_total`。
例如 `seckill.request.queued` → `seckill_request_queued_total`。

| 指标 | 类型 | 建议告警 |
|---|---|---|
| `seckill_outbox_pending` | Gauge（数据库事实，30s 刷新） | 持续 > 0 且不下降 → 投递器追不上或 Broker 不可用 |
| `seckill_outbox_failed` | Gauge | > 0 持续 5 分钟 → 有预扣需要人工核对 |
| `seckill_compensate_pending` | Gauge | 持续 > 0 且不下降 → 归还动作卡住（Redis 不可用？） |
| `seckill_compensate_abandoned_total` | Counter | `increase(...[10m]) > 0` → 有库存需要人工核账 |
| `seckill_reconcile_findings_total{status="..."}` | Counter（按结论分标签） | `increase(...{status="ABANDONED_PENDING"}[10m]) > 0` → 有僵尸预订单 |
| `seckill_consume_confirmed_total` | Counter | `rate(...[1m])` 是结算吞吐（历史实测约 152~157 单/秒，天花板是 stock 行锁） |
| `seckill_consume_order_missing_total` / `seckill_consume_failed_total` | Counter | 任何增长都要人看 |
| `seckill_mq_send_failed_total` | Counter | `increase(...[5m]) > 0` → Broker 侧有问题 |

### 7.2 「看到 X 该怎么办」速查

| 现象 | 先查 | 再决定 |
|---|---|---|
| 用户说「抢到了但查不到结果」 | `GET /seckill/order/status?orderNo=&userId=&stockId=` | 返回 `QUEUED` → 看 outbox 状态；返回 `FAILED` → 看 `compensate_task` |
| `outboxPending` 不降 | `SELECT status, COUNT(*) FROM seckill_outbox WHERE stock_id=? GROUP BY status;` | 若大批 `PENDING` 且 `last_error` 是连接类异常 → Broker 问题；恢复后自动补投 |
| `outboxFailed` 增长 | `SELECT * FROM seckill_outbox WHERE stock_id=? AND status='FAILED';` | 确认对应的 `compensate_task` 是否已 DONE；未 DONE 的看 `last_error` |
| 对账报 `ABANDONED_PENDING` | `SELECT o.order_no FROM orders o JOIN seckill_outbox x ON x.order_no=o.order_no WHERE o.stock_id=? AND o.status='PENDING' AND x.status='FAILED';` | 用 `GET /seckill/reconcile?stockId=1&repair=true` 补登记待办（幂等）；或手工登记 |
| 对账报 `STALE_PENDING` | `SELECT * FROM orders WHERE stock_id=? AND status='PENDING' AND create_time < NOW() - INTERVAL 90 MINUTE;` | **先确认消费者是否只是积压**（看 `rate(seckill_consume_confirmed_total[1m])`）；确认卡死再 repair |
| 对账报 `REDIS_AHEAD` | `GET /seckill/remain?stockId=` 与 `GET /stock/{id}` 对比 | 若确实有降级写库发生过 → `repair=true` 校准（注意闸门） |
| 对账报 `REDIS_BEHIND` | 同上；先排除读偏斜（活动是否正在跑量） | 差值极小且正在跑量 → 下一轮再看；持续存在 → repair |
| `compensatePending` 不降 | `SELECT * FROM compensate_task WHERE stock_id=? AND status<>'DONE';` | `last_error` 里 Redis 连接类 → Redis 问题；`订单不处于可取消状态` → 订单已被确认，这条待办需要人工判断 |
| 用户不能重抢（`REPEAT_ORDER`） | `SELECT * FROM orders WHERE user_id=? AND stock_id=?;` | 该用户在库里有一行订单（含 CANCELLED）→ 这是设计取向（宁可少卖），不是 bug |

### 7.3 常用操作

```bash
# 活动开始前：必须预热，否则下单直接返回 1003
curl -X POST 'http://127.0.0.1:8081/seckill/preheat?stockId=1'

# 手动对账（只报告）
curl 'http://127.0.0.1:8081/seckill/reconcile?stockId=1'
# 手动对账 + 执行修复（三类动作，各有闸门）
curl 'http://127.0.0.1:8081/seckill/reconcile?stockId=1&repair=true'

# 看人读视图（含对账结论计数）
curl 'http://127.0.0.1:8081/seckill/metrics'

# 活动结束：清 Redis 缓存（stock 与 bought；去重键带 TTL 会自行回收）
curl -X DELETE 'http://127.0.0.1:8081/seckill/cache?stockId=1'
```

### 7.4 上线前必须确认的三件事

1. **`stale-pending-minutes` 与你的重试配置匹配**：它必须大于「投递最坏重试时长 + 消费重试时长」。
   默认投递 15 次（14 次等待合计 1150 秒 ≈ 19 分钟）+ 消费重试 ≈ 2 分钟，因此默认 90 分钟留了约 4 倍余量。
   把 `outbox.max-retry` 调大而不动这个阈值，
   就会把还活着的单误判成陈旧（提前收回库存、取消用户订单）。
2. **`auto-repair` 保持 `false` 直到你确认对账判据可信**（尤其是活动正在跑量时）。
   打开后它会自行改 Redis 库存与补登记待办——虽然每个动作都有闸门，但闸门的前提是配置正确。
3. **`seckill.worker-id` 多实例必须各不相同**，否则单号重复（建单会撞 `uk_order_no`，走 #13 的路径）。

## 8. 配置速查（含「调它会怎样」）

| 配置 | 默认 | 调它的后果 |
|---|---|---|
| `seckill.mq.enabled` | `true` | `false` → 不创建任何 MQ 客户端，链路退化为「Redis 预扣 + 同步落库」（本机没 Broker 时可用） |
| `seckill.mq.max-reconsume-times` | `3` | 消费侧重试次数；调大只会拉长「失败 → 归还」的时间，测试环境常配 1 |
| `seckill.outbox.enabled` | `true` | `false` → 请求线程直投 MQ，放弃「消息一定投出」的凭据（见 1.1） |
| `seckill.outbox.dispatch-interval-ms` | `1000` | 决定「落库 → 进 MQ」的额外延迟 |
| `seckill.outbox.batch-size` | `500` | 投递吞吐 ≈ batch-size / 秒；上界受 RocketMQ 批量消息 1MB 约束 |
| `seckill.outbox.max-retry` | `15` | 与 `stale-pending-minutes` **必须一起调**（见 7.4） |
| `seckill.outbox.first-retry-delay-seconds` | `2` | 退避起点；之后 `base << min(attempts,6)`，再夹到 5 分钟上限（`base=2` 时最大 128s，上限不生效） |
| `seckill.outbox.retention-hours` | `24` | 归档窗口；只影响 `SENT` 记录，欠账凭据不删 |
| `seckill.maintenance.enabled` | `true` | `false` → 不注册维护任务（待补偿 + 对账）；**不影响** Outbox 投递器 |
| `seckill.maintenance.compensate.interval-ms` | `30000` | 待补偿扫描频率（真正时机由每行 `next_retry_time` 决定） |
| `seckill.maintenance.compensate.max-retry` | `10` | 归还动作的重试上限；耗尽 → `FAILED` 等人工 |
| `seckill.maintenance.reconcile.interval-ms` | `300000` | 对账频率；调小只会增加 Redis/DB 读取，不会让结论更及时（门控会挡） |
| `seckill.maintenance.reconcile.auto-repair` | `false` | 见 7.4 第 2 条 |
| `seckill.maintenance.reconcile.stale-pending-minutes` | `90` | 陈旧阈值；**同时**决定排空门控的封顶时长 |
| `seckill.maintenance.reconcile.stock-ids` | `1` | 纳入自动对账的活动；留空则只能手动对账 |
| `seckill.worker-id` | `0` | Snowflake 机器位，多实例必须不同 |

## 10. 已知取舍与残留风险（诚实清单）

1. **「预扣成功 ↔ 建单事务提交」之间崩溃会丢预扣**，且对账不可发现（3.4 节第 1 条）。
   彻底消除需让预扣本身可恢复，属另一层取舍（等于把热点写搬回数据库）。
2. **`outbox.enabled=false` 的对照链路缺少凭据**：那条路径上的僵尸 PENDING 单对账同样报不出来，生产不应开启。
3. **对账结果不落库**：目前只有日志 + 计数器（`seckill_reconcile_findings_total`），没有历史报告表；
   要「查上周三那次不一致」需要接日志系统。
4. **`pipelineDrained` 的第 2 条判据是单实例视角**（`mqSent - resolved` 来自进程内计数）。
   要让它跨实例准确，需要消费成功后回写 outbox 状态。
5. **投递器不做抢占**（没有 `SKIP LOCKED` / claim）：多实例会重复投递，由消费端幂等吸收。
   换来的是零并发控制复杂度；要消除只需替换 `OutboxMessageMapper.selectPending` 一处。
6. **消息重试耗尽后直接 ACK**（不进死信队列）：因为此时订单已取消、库存已归还，重放会造成超卖。
   更稳妥的做法是转投一个「仅供人工审阅、不可自动重放」的 topic。
7. **`STALE_PENDING` 的判定本质是「时间推断」**：阈值再保守也可能误判（例如大促期间消费积压超过 90 分钟）。
   默认 `auto-repair=false`（只告警）就是为了让误判的代价停留在「一条需要人工核对的报告」。
8. **待补偿任务的归还依赖 Redis 可用**：Redis 长时间不可用时，这些任务会重试到上限并置 `FAILED`；
   对账会把它们算作「未了结的归还义务」，因此**不会**贸然校准库存 —— 那部分需要人工介入。
